## 슬라이드 2 — 문제 정의

**입력**: 에이전트 세션의 한 시점 스냅샷
- `current_prompt` — 현재 사용자 발화 (한/영/혼용)
- `history` — 이전 행동·결과·대화 시퀀스
- `session_meta` — turn, 경과시간, CI 상태, git 상태, 열린 파일 등

**출력**: 다음 행동 14클래스 분류 (read_file, edit_file, run_tests, web_search …)

**평가·제약**:
| 항목 | 내용 | 전략적 의미 |
|---|---|---|
| 지표 | **Macro-F1** | 소수 클래스가 순위를 가름 |
| 서버 | T4 GPU(16GB), 3 vCPU, **추론 10분 제한**, 인터넷 차단 | 모델을 zip에 포함, 경량화 필수 |
| 용량 | 제출 zip ≤ 1GB | 대형 앙상블 불가 → 어휘 축소로 해결 |
| 제출 방식 | CSV가 아닌 **코드(zip) 제출** — 서버가 script.py 실행 | 안정성·폴백 설계도 점수의 일부 |

## 슬라이드 3 — 데이터 분석 ① 신호의 발견 (심사: 데이터 분석)

train 70,000건 직접 분석 → **베이스라인이 버리는 신호 2가지를 정량 확인**

| 발견 | 근거 수치 |
|---|---|
| 행동 전이 패턴이 뚜렷 | write_file→edit_file 40%, read_file→edit_file 29% |
| 단, 직전 행동 단독으론 부족 | 단독 정확도 23% → **텍스트와 결합해야 유효** |
| 첫 턴은 분포가 다름 | plan_task 비중 전체 3.8% vs 첫 턴 12% (3배) |
| CI 실패 시 행동 편향 | edit_file/run_tests 비중 상승 |
| 클래스 불균형 9배 | edit_file 11,171 vs web_search 1,273 |

→ 검증 실험: prompt만 0.437 → **행동 이력+메타 토큰 추가 시 0.611 (+0.17)**
**결론: 신호 = ① prompt 텍스트 ② 행동 시퀀스 ③ 메타. 셋을 모두 쓰는 모델 설계로 직행**

## 슬라이드 4 — 데이터 분석 ② 누수 검증 (심사: 데이터 분석)

**의심**: id가 `sess_..._step_XX` 구조 → 같은 세션의 다른 step이 train에 공존

- 세션 내 다른 step의 history에 **정답이 그대로 기록**되어 있음을 발견
  - train 기준 커버리지 86.6%, 조회 정확도 **100%**
- **실험으로 확인**: 조회 오버라이드를 넣은 제출 = 안 넣은 제출과 LB 점수 동일
  - → **평가 데이터는 세션당 1개 step만 출제, 누수 차단 확인**
- 교훈: 누수 후보는 "쓰지 말자"가 아니라 **제출 실험으로 존재 여부를 검증**하고 안전하게 유지 (최종 모델에도 무해한 오버라이드로 잔존 — 커버 0이면 무영향)

## 슬라이드 5 — 데이터 분석 ③ 라벨 모호성 분석 (심사: 데이터 분석)

- 동일 발화·유사 상황에서 서로 다른 정답 → **라벨 자체의 모호성** 존재를 정량 확인
  (예: 중복 발화 그룹에서 정답이 갈리는 비율 측정 → 순수 텍스트 신호의 상한이 낮음)
- 실제 리더보드도 상위권이 0.79~0.80 구간에 밀집 — 분석과 부합
- 전략적 의미: 후반전은 "더 큰 모델"이 아니라 **모호 구간의 마진 싸움** → 단일 모델 스케일업 대신 앙상블·표현 다양성으로 전환한 근거

## 슬라이드 6 — 모델 검증 체계 (심사: 모델 검증)

**원칙: 모든 채택/기각은 고정된 검증 분할의 Macro-F1로만 결정**

1. **세션 분리 검증**: GroupShuffleSplit(세션 ID 기준, seed 고정, val 14,106건)
   - 같은 세션이 train/val에 갈리면 점수 과대평가 → 원천 차단
2. **검증→LB 매핑 추적**: 초기 4연속 제출에서 LB = 검증 +0.005 일관 확인 → 검증 신뢰 확보
3. **검증이 못 보는 영역은 LB 프로빙**: 후처리 축(가중치·온도)은 검증 차이 ≤0.002가 노이즈임을 확인 → 소량 프로브 제출로 정점 탐색
4. **과적합 조기 검출 사례**
   - 클래스별 scale: 검증 +인데 LB − → 즉시 제거 (+0.0013 회복)
   - train-subset 전수 탐색(41만 조합) 최고 조합: 로컬 0.812 → LB 0.795 → **로컬-LB 상관 0.20 실측, 기각**
   - 메타 게이트(70k OOF): 전체 학습 확률의 잠재 누수로 LB -0.005 → 학습형 메타 전면 폐기

## 슬라이드 9 — 모델 알고리즘 ② 핵심 기여 1: ID토큰 직렬화 (+0.011)

**문제**: LGBM 최강 피처가 "세션 번호" — 트랜스포머는 이를 못 봄
**해결**: 세션번호를 서브워드 친화 토큰으로 분해해 입력 직렬화에 주입

```
[SID_4217] [STEP_03] [SIDMOD_17] [META] ci=failed turn=6 ...
[HIST] read_file(ok) -> grep_search(17 matches)
[PROMPT] 현재 사용자 발화
```

- 트랜스포머가 LGBM의 구조 신호를 흡수 → LGBM 의존 하락 (최적 가중치 0.4→0.2, 최종 0.10까지 LB 실측으로 확정)
- 단일 기법 최대 LB 기여: **+0.011**
- 파생 발견: ID토큰(v2) vs 신호토큰(v3)은 **서로 다른 오류를 냄** → 이종 직렬화 앙상블의 토대

---

## 슬라이드 10 — 모델 알고리즘 ③ 핵심 기여 2: 선택적 게이트 앙상블

**아이디어: 모든 행에 모든 모델을 쓰지 않는다 — 어려운 행만 추가 의견**

```
        [기본 2모델]                    [판정단]
  s77(v2·ID토큰)  s7(v3·신호토큰)
        │합의 → 그대로 채택 (대부분의 행)
        │이견 (~5%)
        ▼
  s99(v2) judge w0.20 투입
        ▼
  s123(v3)이 judge와 같은 답 + 코어 한쪽 지지 시
  consensus w0.15 추가 (4-way 합의 게이트)
```

- 효과: LB 0.79596 → 0.79629(judge) → 0.79667(consensus) → **0.79677**(가중 최적화)
- 부수 효과: 추가 모델은 이견 행에서만 추론 → **서버 시간 예산 절약**
- 시드·직렬화가 다른 모델의 **불일치 정보 자체를 신호로 활용**한 설계

## 슬라이드 11 — 모델 알고리즘 ④ 최종 아키텍처 (g4_c15)

```
입력 → ┬ LightGBM (TF-IDF 스태킹 + 구조/ID 피처)      w=0.10
       ├ mmBERT s77 — v2 ID토큰 직렬화                w=0.45
       ├ mmBERT s7  — v3 신호토큰 직렬화              w=0.25 (게이트 미작동 시 0.45)
       ├ mmBERT s99 — v2, 코어 이견 행만              w=0.20
       └ mmBERT s123 — v3, 합의 통과 행만             w=0.15
   → 온도 보정(t=0.28) → 가중 평균(행별 재정규화) → argmax
   → 세션 조회 오버라이드(안전판) → 제출
```

**폴백 설계**: 어떤 모델이 실패/시간 초과해도 남은 소스만으로 자동 재정규화 → 서버 이상 상황에서도 제출 실패 0회

## 슬라이드 13 — 실패에서 배운 것 (신뢰성 어필)

| 시도 | 결과 | 교훈 |
|---|---|---|
| 클래스별 scale 후처리 | 검증 +, LB − | 검증 과적합은 LB 프로브로 검출 |
| 모델 soup | 붕괴(0.7645) | 시드 다른 모델은 가중치 평균 불가 |

## 부록 — 발표 시 예상 질문 대비

- **Q. 왜 LGBM 가중치가 0.10뿐인가?** ID토큰 직렬화 후 트랜스포머가 LGBM의 구조 신호를 흡수했고, LB 프로브로 0.10이 정점임을 실측(0.07/0.13 양옆 하락).
- **Q. 게이트 임계값은 어떻게 정했나?** 이견 여부는 하이퍼파라미터가 아닌 구조적 조건. judge/consensus 가중치는 LB 프로브로 정점 확인(0.20/0.15).
- **Q. 세션 조회 오버라이드는 누수 아닌가?** 평가 데이터에 커버 0임을 제출 실험으로 확인했고(점수 불변), 커버 0이면 무영향인 안전 설계.
- **Q. 검증 점수와 LB가 다른데 뭘 믿었나?** 큰 방향(>0.003)은 검증, 미세 축(≤0.002)은 LB 프로브 — 축마다 신뢰 도구를 달리함.
- **Q. LB 프로빙은 public 과적합 아닌가?** 이 대회는 private 분할이 없고 **Public = 전체 테스트 100% 채점 = 최종 점수**. LB에 맞추는 것이 곧 실제 목적함수 최적화이며, 제출 한도 내에서 운용함.

## 부록 2 — 대회 규정 준수 확인 (심사 대비)

| 규정 | 준수 내용 |
|---|---|
| 코드 제출 구조 (model/ + script.py + requirements.txt만) | 전 제출물 동일 구조, 제출 전 체크리스트 운용 |
| script.py는 추론만 수행 | 학습은 전부 로컬, 서버에서는 로드→예측→저장만 |
| 오프라인 환경 (외부 다운로드 금지) | 사전학습 백본 가중치를 zip에 포함(공식 가이드의 권장 방식), 상대 경로만 사용 |
| 외부 데이터 미사용 | 학습은 제공된 train 70,000건만 사용. 사전학습 모델은 공개 가중치(규정상 라이브러리·모델 자유) |
| 추론 10분 / zip 1GB | 최종 885MB, 어휘 축소·fp16·버킷팅으로 시간 확보 + deadline 폴백 |
| 세션 조회 로직의 적법성 | 제공된 test 입력 내부의 history만 사용(외부 정보 없음). 제출 실험으로 평가 데이터 커버 0 확인 — 발동하지 않는 안전판 |
| 재현성 | 모든 seed·라이브러리 버전 고정, 학습 스크립트·실험 로그 전체 보존 |
