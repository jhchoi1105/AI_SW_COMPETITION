## 0. 먼저 — 색과 선 읽는 법

그림은 색 세 가지만 씁니다. 이 규칙만 알아도 흐름의 절반이 읽힙니다.

| 색 | 의미 | 해당 요소 |
|---|---|---|
| **회색** | 중립 — 항상 도는 것, 입력과 출력 | 입력 ①, LightGBM ②, 결합 ⑨, 출력 ⑩ |
| **파랑** | **코어 경로** — 모든 행에서 항상 실행 | mmBERT s77 ③, mmBERT s7 ④, 일치 경로 ⑥ |
| **마젠타** | **게이트 경로** — 조건을 만족한 행에서만 실행 | 게이트 판정 ⑤, judge ⑦, consensus ⑧ |

> **한 문장 요약**: 파란 선은 30,000건 전부가 지나가고, **마젠타 선은 약 1,500건(5%)만 지나갑니다.**

선의 굵기와 화살표는 모두 같은 의미(데이터가 흐르는 방향)이며, 유일하게 다른 모양인
**마름모(⑤)만 "판정"**을 뜻합니다.

## ① 입력 — 에이전트 세션 스냅샷

**무엇인가**
평가 서버가 준 `test.jsonl`의 한 줄. 한 줄이 곧 하나의 예측 대상입니다.

- `current_prompt` — 방금 사용자가 한 말
- `history` — 지금까지의 대화·행동 기록 (0~12개)
- `session_meta` — 턴 번호, CI 상태, git 변경 여부, 열린 파일 등

**왜 이 셋인가**
데이터 분석에서 확인한 **신호 3원천**이 그대로 입력이 됩니다. 대회 베이스라인은 이 중
`current_prompt` 하나만 썼고, 그게 0.43에 머문 이유였습니다.

**발표 한 문장**
> "입력은 에이전트 세션의 한 시점 스냅샷이고, 발화·이력·메타 세 가지를 모두 씁니다."

## ② LightGBM — 항상 도는 기준선 (w 0.10)

**무엇인가**
표 형태 피처를 다루는 결정 트리 기반 모델. 피처 **87개**를 씁니다.

- 텍스트 OOF 확률 14 (TF-IDF+LogReg의 예측을 피처로 넣는 **스태킹**)
- 구조 피처 49 + 탐색 계열 표적 피처 11 + ID 피처 13

**가중치가 0.10뿐인데 왜 남겨두나 — 두 가지 이유**

1. **ID토큰 직렬화 이후 역할이 줄었습니다.** 트랜스포머가 LightGBM의 구조 신호를 흡수하면서
   최적 가중치가 0.4 → 0.2 → 0.10까지 내려갔고, 0.07과 0.13은 양쪽 다 리더보드가 하락해
   0.10이 정점임을 실측했습니다.
2. **폴백 기준선입니다.** 그림에서 LightGBM만 회색 선으로 왼쪽 끝까지 **곧장 내려가는 것**을
   보세요. 트랜스포머가 전부 실패해도 이 경로 하나로 답이 나갑니다.

**질문 대비**
> Q. 0.10이면 빼도 되지 않나?
> → 성능 기여는 작지만 **안정성 측면에서 필수**입니다. 10분 마감에 걸린 행은 LightGBM 예측이
> 그대로 나갑니다.

## ③ mmBERT s77 — 코어 1 (v2 직렬화, w 0.45)

**무엇인가**
다국어 백본 `jhu-clsp/mmBERT-base`를 우리 데이터로 파인튜닝한 모델. **시드 77**.

**v2 직렬화란**
입력 세 가지를 하나의 긴 문자열로 합칠 때 **ID토큰을 맨 앞에 붙인** 방식입니다.

```
SID 28750 STEP 2 M256_98 M100_50 M64_34 M16_2 | 프롬프트 || 메타 토큰 || 최근순 이력
```

**왜 가중치가 가장 높은가**
5개 소스 중 **단일 최고 성능**이라 LB 프로브로 0.45가 정점임을 확인했습니다.
`s7 + seed77` 조합이 `s7 + seed123`, `s7 + seed26`보다 우수해서 코어로 고정됐습니다.

## ④ mmBERT s7 — 코어 2 (v3 직렬화, w 0.25 / 0.45)

**무엇인가**
같은 백본, **시드 7**, 그리고 **v3 직렬화**를 쓴 모델.

**v3 직렬화란 (v2와의 차이 — 자주 묻습니다)**

| | 구성 |
|---|---|
| **v2** (③) | ID토큰 + 기본 직렬화 |
| **v3** (④) | ID토큰 + **구조 신호 토큰** + 기본 직렬화 |

구조 신호 토큰은 LightGBM이 강하게 쓰던 신호를 명시적 토큰으로 만든 것입니다.
```
CIF_failed DIRTY_1 NOPEN_2 EXT_py NACT_4 RES_fail PREV_read_file SEQ_read_file>edit_file
```

**핵심 — 왜 두 개를 다르게 만들었나**
두 모델은 **성능이 비슷한데 틀리는 문제가 다릅니다.** 앙상블의 이득은 성능이 아니라
**서로 다른 실수**에서 나옵니다. 실측으로 시드만 다른 모델끼리는 이견율이 7.3%인데,
직렬화가 다르면 13.5%까지 올라갔습니다.

**⚠️ 오른쪽의 회색 주석 — "게이트 미작동 시 w 0.45로 자동 복귀"**

이 부분이 그림에서 가장 오해하기 쉬운 곳입니다. 정확한 동작은 이렇습니다.

| 행의 종류 | s7의 가중치 |
|---|---|
| **코어 2모델이 일치한 행 (약 95%)** | **0.45** |
| 코어 2모델이 갈린 행 (약 5%) | 0.25 |

즉 0.25는 **게이트가 열린 5%에서만** 쓰는 값입니다. 게이트가 열리지 않은 행이나
게이트 모델이 실패한 행에서는 자동으로 0.45로 돌아갑니다.

**여기서 설계의 우아한 점** — `0.25 + 0.20(judge) = 0.45`입니다.
judge가 들어올 때 **s7이 내놓은 0.20만큼을 judge가 가져가는** 구조라, 두 경우 모두
가중치 합이 정확히 **1.00**으로 유지됩니다.

```
일치 행 : 0.10 + 0.45 + 0.45              = 1.00
이견 행 : 0.10 + 0.45 + 0.25 + 0.20       = 1.00
  + consensus 통과 시 0.15가 더해져 1.15 → 재정규화
```

## ⑤ 게이트 판정 — "두 모델의 예측이 같은가?"

**무엇인가**
코어 두 모델의 **argmax(최종 선택 클래스)가 같은지**만 보는 이진 판정.

**정확한 조건 (코드 기준)**
```
게이트 열림 = (s77이 처리됨) AND (s7이 처리됨) AND (s77의 답 ≠ s7의 답)
```
두 모델 **모두 시간 안에 처리된 행**에서만 판정합니다. 한쪽이 마감에 걸린 행은
게이트를 열지 않습니다.

**질문 대비 — 가장 자주 나오는 질문입니다**
> Q. 게이트 임계값은 어떻게 정했나요?
> → **임계값이 아니라 구조적 조건입니다.** 두 모델의 답이 같은가 다른가라는 이진 판정이라
> 튜닝할 하이퍼파라미터가 없습니다. 튜닝한 건 judge와 consensus의 **가중치**뿐입니다.

**점선 상자(불일치 자체를 난이도 신호로 쓴다)가 여기 있는 이유**
보통은 "이 입력이 어려운가"를 판별하는 별도의 모델을 만듭니다. 저희는 **두 모델이 갈린다는
사실 자체**를 난이도 신호로 썼기 때문에 그런 판별기가 필요 없었습니다.

## ⑥ 일치 경로 — 약 95%는 여기서 끝

**무엇인가**
두 코어가 같은 답을 낸 행. 왼쪽 파란 선을 타고 **추가 모델 없이 곧장 결합(⑨)** 으로 갑니다.

**왜 그냥 채택하는가**
두 모델이 이미 합의한 구간은 대부분 맞히고 있어서 개선 여지가 거의 없습니다.
남은 개선 여지는 갈리는 5%에 몰려 있었고, 계산 자원을 거기에만 집중한 것이 이 설계입니다.

**질문 대비**
> Q. 5%만 건드리면 개선 폭이 너무 작지 않나?
> → 맞습니다. 그리고 그게 의도입니다. 이 시점에 저희는 이미 0.796 구간이었고 상위권이
> 0.79~0.80에 밀집해 있었습니다. 실제로 0.79596 → 0.79677의 계단식 상승을 만들었습니다.

## ⑦ mmBERT s99 — judge (w 0.20)

**무엇인가**
코어 두 모델이 갈린 **약 5%의 행에만** 투입되는 세 번째 모델. 시드 99, v2 직렬화.

**"judge"라고 부르지만 판사가 아닙니다 — 중요**
judge는 답을 **뒤집는 게 아니라 0.20짜리 한 표를 더하는** 것입니다.
가중치를 무한대로 주는 하드 오버라이드 방식도 실험했지만
(`g4_hard`, LB 0.79663) champion보다 **낮아서 기각**했습니다.

**왜 seed99인가**
seed202, seed303, seed404, seed2026, XLM-R, mDeBERTa, Alibaba 등 여러 후보를 judge 자리에
넣어 제출로 비교했고, **seed99가 가장 좋았습니다.** 가중치도 0.15·0.25보다 0.20이 우수했습니다.

**부수 효과 (발표에서 꼭 언급)**
5%에서만 도니까 **서버 10분 예산이 절약**됩니다. 5개를 전부 돌렸다면 시간 안에 못 끝냈습니다.

## ⑧ mmBERT s123 — consensus (w 0.15)

**무엇인가**
네 번째 모델. 시드 123, v3 직렬화. judge와 **같은 행**에서 돌지만,
**두 조건을 모두 만족할 때만** 의견이 반영됩니다.

**정확한 조건 (코드 기준)**
```
① s123의 답 == s99(judge)의 답            ← 심판과 의견이 같고
② 그 답이 s77 또는 s7의 답과도 일치        ← 원래 후보 안에 있고
   (+ 네 모델 모두 그 행을 정상 처리했을 것)
```
조건을 못 채우면 s123의 확률은 **버립니다.**

**왜 이렇게 까다롭게 걸었나**
judge 하나만으로는 "심판도 틀릴" 위험이 있습니다. 네 번째 모델이 심판과 같은 답을 내면서
**동시에 원래 후보 중 하나**여야 한다는 이중 조건을 걸면, 완전히 엉뚱한 답으로 끌려갈
위험 없이 확신도만 높일 수 있습니다.

**이 가중치 하나가 champion을 만들었습니다**
`g4_cons`(consensus 0.10) 0.79667 → **`g4_c15`(consensus 0.15) 0.7967670316**.
최종 제출물의 이름 `c15`가 바로 이 **0.15**입니다.

## ⑨ 결합 — 온도 보정 → 가중 평균 → argmax

**무엇인가**
모인 확률들을 하나로 합쳐 최종 클래스를 고르는 단계.

**세 동작을 순서대로**

**1) 온도 보정 (t = 0.28)**
각 확률에 0.28 제곱을 하고 다시 합이 1이 되게 정규화합니다.
- 0.9 → 0.9^0.28 ≈ 0.97 / 0.1 → 0.1^0.28 ≈ 0.53 → **격차가 줄어듦 = 분포가 평평해짐**
- **왜?** 한 모델이 지나치게 확신하면 앙상블에서 독주합니다. 평평하게 만들어야 다른 모델의
  2·3순위 의견까지 섞입니다.
- **⚠️ 온도는 트랜스포머 4개에만 적용됩니다.** LightGBM 확률은 그대로 들어갑니다.
  그림의 결합 상자에 "온도 보정"이 한 번에 쓰여 있어 오해하기 쉬운 부분입니다.

**2) 행별 가중 평균 (재정규화)**
```
분자 = 0.10 × LGBM + Σ (가중치 × 확률)     ← 그 행에서 처리된 모델만
분모 = 0.10        + Σ (가중치)             ← 그 행에서 처리된 모델만
최종 확률 = 분자 / 분모
```
**"행별"이 핵심입니다.** 30,000행이 모두 같은 공식을 쓰는 게 아니라, 각 행마다 실제로
답을 낸 소스만 모아 그 가중치 합으로 나눕니다. 그래서 모델이 빠져도 확률의 총량이
무너지지 않습니다.

**3) argmax**
14개 확률 중 가장 큰 것을 최종 예측으로 선택합니다.

**질문 대비**
> Q. 재정규화가 없으면 어떻게 되나?
> → 모델이 빠질 때마다 확률의 총량이 줄어들어 분포가 망가집니다. 남은 가중치의 합으로
> 나눠 다시 합이 1이 되게 맞춰야 합니다.

## ⑩ 출력 — 다음 행동 1개 · 14클래스

**무엇인가**
`output/submission.csv`에 들어갈 최종 예측. `id, action` 두 컬럼.

**그림에 없지만 이 뒤에 한 단계 더 있습니다**
argmax 뒤에 **세션 조회 오버라이드**가 붙어 있습니다. 다만 평가 데이터에서 **발동 0건**임을

질문이 나오면 이렇게 답하세요.
> "제공된 test 입력 내부의 history만 보는 안전판이고, 평가 데이터는 세션당 1개 step만
> 출제되어 커버가 0입니다. 넣은 제출과 뺀 제출의 점수가 소수점 10자리까지 같았습니다."

마지막으로 14개 클래스명에 없는 값이 있으면 오류를 내는 **검증 코드**가 돌고 저장됩니다.

## 맨 아래 각주 — 폴백 설계

그림 하단의 회색 한 줄이 실은 **안정성 어필의 핵심**입니다.

| 상황 | 동작 |
|---|---|
| 트랜스포머 로드 실패 | 그 모델만 빼고 남은 소스로 재정규화 |
| 10분 마감 도달 | 처리된 행까지만 반영, 미처리 행은 **LightGBM 예측 유지** |
| 게이트 모델 실패 | s7 가중치가 0.25 → **0.45로 자동 복귀** |
| 전부 실패 | LightGBM 단독 예측 (+ 소수 클래스 보정, `web_search` 1.75배) |

**결과: 대회 전 기간 제출 실패 0회.**

> 마지막 줄의 `web_search` 1.75배 보정은 **LightGBM 단독 폴백 경로에서만** 적용됩니다.
> 정상 경로에서는 클래스별 보정을 쓰지 않습니다 — 검증 과적합으로 확인되어 제거했습니다.

| mmBERT s7 | 시드 7 | v3 | **0.25** (게이트 미개방 시 0.45) | 항상 |
| mmBERT s99 | 시드 99 | v2 | **0.20** | 이견 행 (약 5%) |
| mmBERT s123 | 시드 123 | v3 | **0.15** | 이견 + 합의 통과 행 |

공통 학습 설정: 3에폭 · max_len 512 · batch 16 · lr 3e-5 · 온도 0.28

**게이트가 만든 계단**
```
0.79596  코어 2모델
0.79629  + judge          (+0.00033)
0.79667  + consensus      (+0.00038)
0.79677  + 가중치 0.15    (+0.00010)   ← g4_c15
```

## 설명 스크립트

### 30초 버전 (포스터 앞을 지나가는 사람에게)

> "코딩 에이전트가 다음에 무슨 행동을 할지 맞히는 모델입니다.
> 모델 다섯 개를 쓰는데, **전부 다 돌리지는 않습니다.**
> 기본 두 모델이 같은 답을 내면 거기서 끝내고, **갈리는 5%에만** 세 번째·네 번째 모델을
> 부릅니다. 어려운 문제에만 추가 의견을 받는 구조라 정확도도 오르고 서버 시간도 아꼈습니다."

### 90초 버전 (관심을 보이는 사람에게)

> "왼쪽부터 보시면 LightGBM 하나와 mmBERT 네 개, 총 다섯 소스입니다.
> mmBERT 두 개는 **같은 데이터를 서로 다른 방식으로 정리해서** 학습시켰습니다. 하나는 세션
> 번호만 토큰으로 넣었고, 다른 하나는 구조 신호까지 넣었습니다. 성능은 비슷한데 **틀리는
> 문제가 달라서**, 그 차이가 앙상블의 재료가 됩니다.
>
> 가운데 마름모가 핵심입니다. 두 모델의 답이 같으면 — 전체의 95%인데 — 그대로 채택합니다.
> 갈리는 5%에만 세 번째 모델을 심판으로 부르고, 네 번째 모델은 **심판과 같은 답을 내면서
> 원래 두 모델 중 한쪽도 지지할 때만** 표를 보탭니다.
>
> 마지막에 온도 보정을 하고 가중 평균해서 답을 고르는데, **행마다 실제로 답을 낸 소스만
> 모아서** 재정규화합니다. 그래서 모델 하나가 죽어도 예측이 계속 나갑니다.
> 대회 기간 내내 제출 실패가 한 번도 없었습니다."

### 자세히 물어볼 때 꺼낼 카드

1. **"불일치를 난이도 신호로 썼다"** — 별도 난이도 판별기가 필요 없는 구조 (⑤)
2. **"0.25 + 0.20 = 0.45"** — judge가 s7의 몫을 가져가 합이 1로 유지되는 설계 (④)
3. **"consensus 0.10 → 0.15가 마지막 champion"** — 제출물 이름 `c15`의 유래 (⑧)
4. **"하드 오버라이드는 기각했다"** — judge는 판사가 아니라 한 표 (⑦)

## ⚠️ 자주 하는 잘못된 설명

발표·질의응답에서 실수하기 쉬운 지점입니다. **왼쪽처럼 말하면 안 됩니다.**

| ✗ 잘못된 설명 | ✓ 정확한 설명 |
|---|---|
| "모델 5개를 전부 돌려서 평균냅니다" | 3개는 전부, **2개는 5%에서만** 돕니다 |
| "가중치는 항상 고정입니다" | s7은 행에 따라 **0.25 또는 0.45** |
| "모든 확률에 온도를 적용합니다" | **트랜스포머 4개에만**, LightGBM은 그대로 |
| "judge가 최종 결정을 내립니다" | judge는 **0.20짜리 한 표** — 하드 오버라이드는 기각됨 |
| "네 번째 모델도 항상 들어갑니다" | **조건 두 개를 모두** 만족할 때만 |
| "이견이 나면 다시 학습합니다" | 학습은 전부 로컬에서 끝. 서버는 **추론만** |
| "시드를 다르게 해서 다양성을 얻었습니다" | 다양성은 시드가 아니라 **직렬화(표현)** 에서 — 시드만 다르면 이견율 7.3% |
