# 2026 AI·SW중심대학 디지털 경진대회 (AI부문) — 정리 노트

> AI 코딩 에이전트가 **다음에 취할 행동(action)** 을 예측하는 문제입니다.
> 이 문서는 대회 폴더의 모든 파일을 읽고 이해하기 쉽게 정리한 것입니다.

---

## 1. 한 줄 요약

AI 코딩 에이전트가 사용자와 대화하며 작업하던 도중, **바로 지금 시점에서 어떤 행동을 할지**를
**14개 행동 클래스 중 하나**로 맞히는 **다중 분류(multi-class classification)** 문제입니다.

- **입력**: 세션 정보 + 이전 대화·행동 이력 + 현재 사용자 발화
- **출력**: 14개 action 클래스 중 1개
- **평가지표**: **Macro-F1** (14개 클래스를 모두 동일한 비중으로 평가)

## 6. 평가 방식 — Macro-F1

- **Macro-F1** = 14개 클래스 각각의 F1 점수를 구한 뒤 **동일 가중치로 평균**
- 데이터가 적은 클래스도 자주 등장하는 클래스와 **똑같이 중요**하게 평가됨
- 따라서 다수 클래스만 잘 맞히는 모델은 점수가 낮게 나옴

### 6-1. Macro F1 Score 자세히

Macro F1 Score는 다중 클래스 분류 문제에서 모델의 성능을 평가하는 지표로,
**각 클래스별로 계산된 F1 Score의 평균**을 구하여 전체 성능을 평가합니다.
F1 Score는 Precision과 Recall의 조화 평균으로 계산되며, 모델이 **클래스 불균형
문제를 얼마나 잘 처리하는지** 측정하는 데 도움이 됩니다.

**계산 과정:**

1. 각 클래스에 대해 Precision과 Recall을 계산
2. 각 클래스에 대해 F1 Score를 계산: $F1 = 2 \times \frac{Precision \times Recall}{Precision + Recall}$
3. 모든 클래스에 대한 F1 Score의 평균을 계산

**Python 계산 예제:**

```python
import numpy as np
from sklearn.metrics import f1_score


def macro_f1_score(y_true, y_pred, n_classes):
    f1_scores = []
    for c in range(n_classes):
        y_true_c = (y_true == c)
        y_pred_c = (y_pred == c)
        f1_c = f1_score(y_true_c, y_pred_c)
        f1_scores.append(f1_c)
    return np.mean(f1_scores)


# 샘플 데이터
y_true = np.array([0, 1, 2, 0, 1, 2, 0, 1, 2])
y_pred = np.array([0, 1, 1, 0, 1, 2, 0, 1, 1])

# Macro F1 Score 계산
n_classes = 3
macro_f1 = macro_f1_score(y_true, y_pred, n_classes)
print("Macro F1 Score:", macro_f1)
```

> 참고: `sklearn`에서는 `f1_score(y_true, y_pred, average="macro")` 한 줄로도 동일하게 계산됩니다.
> 이 대회 기준으로는 14개 클래스 각각의 F1을 구해 평균하는 것이므로, 소수 클래스
> (web_search 1,273건)의 F1 하나가 다수 클래스(edit_file 11,171건)의 F1과 정확히
> 같은 무게로 최종 점수에 반영됩니다.

## 7. ⭐ 제출 방식 (매우 중요)

이 대회는 **결과 CSV가 아니라 '코드'를 제출**합니다.

1. 아래 구조로 **zip 파일**을 만들어 제출:
   ```
   submit.zip
   ├── model/               # (선택) 학습해 둔 모델 파일
   │   └── your_model.pkl
   ├── script.py            # 평가 서버가 그대로 실행하는 추론 코드
   └── requirements.txt     # 필요한 라이브러리
   ```
2. 평가 서버가 zip을 풀고 **`script.py`를 그대로 실행**하여 채점
3. 서버는 `./data/test.jsonl`(실제 30,000건)과 `./data/sample_submission.csv`를 제공
4. `script.py`는 **`./output/submission.csv`** 를 만들어 내야 함

> 즉, **모델 학습은 로컬에서 미리 하고**, 제출한 `script.py`는 그 모델을 불러와
> 서버가 준 test 데이터에 대해 예측만 수행하는 구조입니다.
> (원한다면 script.py 안에서 직접 학습하도록 짤 수도 있음)

## 8. 베이스라인 코드가 하는 일

베이스라인은 **가장 단순한 접근**으로, 여러 정보 중 **`current_prompt` 텍스트만** 사용합니다.

### 학습 (`...(학습).ipynb`)
1. `train.jsonl` + `train_labels.csv`를 id로 연결 → `X = current_prompt`, `y = action`
2. train/val 8:2 분할 (`stratify=y`로 클래스 비율 유지)
3. **파이프라인**: `TF-IDF` (1~2gram, min_df=2, max_features=80,000, sublinear_tf) → `LogisticRegression` (class_weight='balanced', C=2.0)
4. 검증 세트로 Macro-F1 확인
5. **전체 데이터로 재학습** 후 `./model/tfidf_logreg.pkl` 저장

### 추론 (`script.py`)
1. 저장한 모델 로드
2. `test.jsonl`에서 `current_prompt`만 추출 (학습과 동일하게)
3. `model.predict()` 로 예측
4. `sample_submission.csv`의 id 순서에 맞춰 `./output/submission.csv` 생성

### 사용 라이브러리
```
scikit-learn==1.8.0
joblib==1.5.3
```

## 9. 성능을 올리려면 (개선 아이디어)

베이스라인은 `current_prompt` **하나의 텍스트만** 쓰기 때문에, 아직 활용하지 않은 정보가 많습니다.

- **history 활용**: 직전 행동/대화 흐름은 다음 행동 예측에 강력한 단서
  (예: 방금 `read_file` 했으면 다음은 `edit_file`일 가능성이 높음)
- **session_meta 피처화**: turn_index, last_ci_status(failed면 run_tests?), git_dirty, open_files 유무, language_pref 등
- **텍스트 개선**: current_prompt + 직전 발화들을 이어붙이기, 다국어(ko/en/mixed) 처리
- **모델 교체**: LightGBM/XGBoost 같은 부스팅, 또는 다국어 트랜스포머(예: multilingual BERT) 파인튜닝
- **클래스 불균형 대응**: 소수 클래스 가중치·오버샘플링 (Macro-F1이므로 특히 중요)
- **검증 전략**: 세션 단위 분리 검증으로 과적합 방지

## 12. DACON 코드 제출 대회 공식 가이드 (요약)

### 12-1. 왜 코드 제출 방식인가

- **공정성**: 평가 데이터 X(입력)를 참가자에게 공개하지 않고 서버에서 직접 실행·평가 → 평가 데이터 특화 편법/과적합/치팅 차단
- **종합 평가**: 정확도뿐 아니라 추론 속도, 메모리 효율, 안정성까지 실제 배포 환경과 유사한 조건에서 측정
- **즉시 활용**: 대회 종료 후 검증된 추론 파이프라인을 바로 실무에 적용 가능

### 12-2. 제출 파일 구조 (엄격히 준수)

```
your_submission.zip   # 파일명 자유 (공백·한글만 제외)
├── model/            # 학습된 모델 가중치 (파일명 자유, 여러 파일 가능)
├── script.py         # 추론 실행 코드 (이 파일명 필수, 추론만 수행)
└── requirements.txt  # 패키지 의존성 (필수)
```

- **최상위에 model/, script.py, requirements.txt만** — 추가 폴더/파일 없어야 함
- `script.py`는 학습 없이 **데이터 로드 → 모델 로드 → 예측 → 결과 저장** 순서로 추론만 수행
- `requirements.txt`: 서버에 **이미 설치된 패키지는 버전 호환이 맞춰져 있으므로 가급적 포함하지 말 것** (권장)
  → ⭐ 우리가 겪은 numpy ABI 충돌 에러의 원인이 바로 이것. 꼭 필요한 추가 패키지만 최소로 명시

### 12-3. 평가 서버 동작 순서

1. **환경 구성**: zip 해제 후 서버가 `data/`(실제 평가 데이터)와 `output/` 폴더를 자동 추가
2. **패키지 설치**: `pip install -r requirements.txt` — 실패 시 **설치 오류 (제출 횟수 차감 없음)**
3. **추론 실행**: `python script.py` — 실패 시 **제출 오류 (제출 횟수 차감됨)**

- 3 vCPU가 약하므로 CPU 무거운 전처리는 시간을 잡아먹음 → 로컬 검증 시 스레드 3개로 제한해서 시간 측정할 것
- torch/transformers 등 대형 패키지는 버전 핀 없이 requirements에 (사전 설치본 활용, 버전 충돌 방지)
- 설치 실패는 횟수 차감이 없으므로, **위험한 건 script.py 런타임 에러와 시간 초과** → 실험적 코드는 try/except로 감싸 안전 폴백 확보

## 14. 평가 데이터에 대해 밝혀진 사실 (제출 실험으로 확인)

- **평가 데이터는 세션당 1개 step만 출제** — train은 세션당 평균 7.4개 step이 있어 같은 세션 다른 샘플의 history에서 정답을 조회(누수)할 수 있었으나(커버 86.5%·정확도 100%), 평가 데이터에서는 이 구조가 차단되어 있음 (조회 오버라이드를 넣은 제출과 뺀 제출의 점수가 소수점 10자리까지 동일함으로 확인)
- **검증↔리더보드 매핑**: 세션 분리 검증(GroupShuffleSplit seed42) 점수 + 약 0.006 ≈ 리더보드 점수 (검증 0.735 → LB 0.7414로 확인). 로컬 검증에서 이기면 리더보드에서도 이김
- 평가 데이터 id는 train과 다른 생성 배치일 수 있음 ("au" 형식 변형 가능성) — id 기반 피처는 이를 감안해 순번·나머지 등 일반화된 형태만 사용
