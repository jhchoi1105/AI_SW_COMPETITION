# 대회 공략 전략 — 다음 행동(action) 예측

> [대회_정리.md](대회_정리.md)를 기반으로, **실제 train 데이터를 분석·실험한 결과**를 근거로 세운 전략입니다.

---

## 0. 사전 분석에서 확인한 사실 (전략의 근거)

로컬에서 train 데이터 70,000건을 직접 분석·실험한 결과입니다.

| 실험 | Macro-F1 (검증 20%) |
|------|---------------------|
| 베이스라인 그대로 (current_prompt만, TF-IDF+LogReg) | **0.437** |
| current_prompt + **직전 행동 3개 + 메타 토큰**을 텍스트에 붙임 | **0.611** (+0.17) |

그 외 발견한 데이터 신호:

- **직전 행동 → 다음 행동 전이 패턴이 뚜렷함**: `write_file → edit_file` 40%, `read_file → edit_file` 29%, `list_directory → read_file` 25%, `edit_file → run_tests` 23%. 다만 직전 행동 **하나만으로는 정확도 23%** → 텍스트와 결합해야 힘을 발휘.
- **첫 턴(history 없음) 9,000건은 분포가 완전히 다름**: `list_directory` 20%, `read_file` 17%, `plan_task` 12% (plan_task는 전체에선 3.8%인데 첫 턴에선 3배 이상).
- **last_ci_status=failed**일 때 `edit_file`/`apply_patch`/`run_tests` 비중 상승.
- **클래스 불균형 9배** (edit_file 11,171 vs web_search 1,273) + 평가가 Macro-F1 → 소수 클래스 관리가 순위를 가름.

**결론: 이 문제의 신호는 ① current_prompt 텍스트(주 신호) ② history의 행동 시퀀스 ③ session_meta(보조 신호) 세 가지이며, 베이스라인은 ①만 쓰고 있다.**

## 1. 전략 로드맵 한눈에 보기

| 단계 | 전략 | 예상 Macro-F1 | 비용 | 리스크 |
|------|------|---------------|------|--------|
| A | 피처 강화 TF-IDF (검증 완료) | 0.61+ | 반나절, CPU만 | 거의 없음 |
| B | LightGBM + 구조적 피처 | 0.62~0.67 | 1~2일, CPU | 낮음 |
| C | 다국어 트랜스포머 파인튜닝 | 0.68~0.75+ | 2~4일, GPU 필요 | 중간 |
| D | 앙상블 (B+C 등) | +0.01~0.03 | 마지막 며칠 | 낮음 |

> 권장 진행: **A로 즉시 제출해 리더보드 기준점 확보 → B와 C를 병행 → 마감 전 D**.
> 각 전략은 독립적이라 팀원이 나눠 맡기 좋습니다.

## 2. 전략 A — 피처 강화 TF-IDF (즉시 실행, 이미 검증됨)

**아이디어**: 베이스라인 구조를 유지하되, history와 meta를 **특수 토큰 문자열**로 만들어 current_prompt에 이어붙인다. TF-IDF가 이 토큰들을 일반 단어처럼 학습한다.

```python
def build_text(s):
    m = s['session_meta']; w = m['workspace']
    acts = [h['name'] for h in s.get('history', []) if h.get('role') == 'assistant_action']
    last3 = ' '.join('PREV_' + a for a in acts[-3:]) if acts else 'PREV_none'
    meta = f"CI_{w['last_ci_status']} TURN_{min(m['turn_index'],5)} DIRTY_{w['git_dirty']} TIER_{m['user_tier']}"
    return s['current_prompt'] + ' || ' + last3 + ' ' + meta
```

이것만으로 **0.437 → 0.611**을 로컬에서 확인했습니다.

**추가 개선 여지** (각각 실험해서 검증 점수로 채택 여부 결정):
- 직전 **사용자 발화**(history의 user content)도 이어붙이기 — 문맥이 이어지는 요청이 많음
- 직전 행동의 `result_summary` 포함 (예: "PASS: 53 tests" / "found 17 matches"는 다음 행동의 강한 힌트)
- 행동 **바이그램** 토큰 (`PREVSEQ_read_file>edit_file` 형태)
- `open_files` 유무·개수, `language_mix` 최대 언어를 토큰화
- char n-gram TF-IDF 추가 (ko/en/mixed 혼용 대응) 후 word TF-IDF와 hstack
- LogisticRegression C 튜닝, LinearSVC와 비교

**산출물**: 첫 제출 zip. 이후 모든 실험의 리더보드 기준점.

## 3. 전략 B — 구조적 피처 + 그래디언트 부스팅 (LightGBM)

**아이디어**: 이 문제는 절반이 **테이블 데이터 문제**다. 텍스트를 벡터로, 메타를 숫자/카테고리로 만들어 LightGBM에 넣으면 TF-IDF+선형모델이 못 잡는 **피처 간 상호작용**(예: "CI failed **이고** 직전이 edit_file이면 run_tests")을 잡는다.

**피처 설계**:

| 그룹 | 피처 |
|------|------|
| 텍스트 | current_prompt의 TF-IDF → SVD 100~300차원 (또는 LogReg 예측확률 14개를 피처로 = 스태킹) |
| 행동 이력 | 직전 1·2·3번째 행동(카테고리), 행동별 등장 횟수 14개, 직전 행동 연속 반복 수, history 길이 |
| 결과 요약 | 마지막 result_summary에 FAIL/PASS/error/found 0 포함 여부 |
| 메타 | turn_index, elapsed_session_sec, budget_tokens_remaining, loc, git_dirty, last_ci_status, user_tier, language_pref, open_files 개수, 주 언어 |
| 발화 패턴 | prompt 길이, 물음표 여부, 명령형 키워드(실행/고쳐/찾아/열어 ko·en 사전) |

**포인트**:
- `class_weight` 또는 소수 클래스 오버샘플링으로 Macro-F1 최적화
- 예측 확률에 클래스별 **threshold 조정**(소수 클래스 recall 확보) — Macro-F1에선 효과 큼
- 피처 중요도로 어떤 신호가 먹히는지 확인 → 전략 A/C에도 환류

**리스크**: 낮음. CPU로 충분하고 requirements에 lightgbm만 추가하면 제출 구조 동일.

## 4. 전략 C — 다국어 트랜스포머 파인튜닝 (최고 성능 후보)

**아이디어**: prompt가 ko/en/mixed 혼용 자연어이므로, TF-IDF보다 **문장 의미를 이해하는 사전학습 모델**이 상한이 높다. 입력을 하나의 시퀀스로 직렬화해 14-클래스 분류로 파인튜닝한다.

**입력 직렬화 예시**:
```
[META] tier=free ci=failed turn=6 dirty=1
[HIST] read_file(ok) -> grep_search(17 matches) -> user: "딥링크 막아야 해..."
[PROMPT] 현재 사용자 발화
```

**모델 후보**:
- `xlm-roberta-base` — 다국어 표준, 무난한 1순위
- `microsoft/mdeberta-v3-base` — 다국어 분류에서 xlm-r보다 좋은 경우 많음
- 한국어 특화(klue/roberta 등)는 en 비중이 높으면 불리할 수 있어 다국어 우선

**학습 팁**:
- max_length 256~384 (history 요약을 짧게 유지), 3~4 epoch, lr 2e-5
- 손실에 클래스 가중치 적용 or Focal Loss — Macro-F1 대응
- 70k건이므로 base 모델 기준 GPU(콜랩 T4 포함)로 1~2시간 내 학습 가능

**제출 시 주의 (중요)**:
- 평가 서버 환경 확인 필요: **GPU 제공 여부, 인터넷 차단 여부, 실행 시간 제한**. 인터넷이 차단이면 모델 가중치를 zip에 포함해야 하고(base 모델 ~1GB), **zip 용량 제한**도 대회 페이지에서 확인할 것.
- CPU만 제공될 경우: 추론 30,000건은 base 모델 CPU로도 수십 분 수준이라 보통 가능하지만, 시간 제한에 따라 distil 계열로 축소 검토.
- 이 확인이 끝나기 전에는 B를 주력으로 유지 (B는 환경 리스크가 없음).

## 5. 전략 D — 앙상블 & 마무리 최적화 (마감 직전)

- **소프트 보팅**: A/B/C 각 모델의 클래스 확률 평균 (가중치는 검증 세트로 탐색)
- **스태킹**: A·C의 예측 확률 14+14개를 B(LightGBM)의 입력 피처로
- **클래스별 threshold/후처리**: 검증 세트에서 Macro-F1이 최대가 되도록 argmax 대신 조정된 결정 규칙 사용
- **시드 앙상블**: 같은 모델을 seed만 바꿔 3~5개 평균 (트랜스포머에서 특히 효과)

## 6. 공통 인프라 — 순위를 지키는 것들

### 6-1. 검증 전략 (가장 먼저 고정할 것)
- id가 `sess_sim_..._-step_XX` 구조 → **같은 세션의 여러 step이 train에 공존**할 가능성. 같은 세션이 train/val에 나뉘면 검증 점수가 과대평가됨.
- **세션 ID 기준 GroupKFold**로 분할하고, 단순 무작위 분할과 점수 차이를 확인할 것. 차이가 크면 반드시 세션 분리 검증 사용.
- 모든 실험은 **동일한 검증 분할**로 비교 (분할이 바뀌면 비교 불가).
    
### 6-2. 오류 분석 루틴
- 검증 세트에서 **클래스별 F1**과 혼동 행렬을 매 실험마다 기록.
- Macro-F1이므로 F1이 낮은 소수 클래스(web_search, write_file, lint_or_typecheck)를 집중 공략 — 이 3개 클래스에서 +0.1씩만 올려도 Macro-F1 +0.02.
- 헷갈리는 쌍(예: edit_file vs apply_patch, grep_search vs glob_pattern)의 오분류 샘플을 직접 읽고 구분 피처 추가.

### 6-3. 제출 파이프라인
- 제출 전 **로컬 리허설**: 깨끗한 폴더에 zip 압축 해제 → `data/`에 test.jsonl 5건 배치 → `pip install -r requirements.txt` 후 `python script.py` 실행 → `output/submission.csv` 생성 확인.
- 예측 클래스명이 14개 클래스와 **대소문자까지 일치**하는지 검증 코드 포함.
- 실험 로그(날짜, 변경점, 검증 F1, 리더보드 F1)를 표로 기록 — 검증↔리더보드 상관을 확인해야 과적합을 조기에 잡음.
- 수상 시 **재현 검증**이 있으므로 random_state 고정, 학습 코드·환경 버전 기록.

## 7. 실행 계획 요약

```
1주차:  [A] 피처 강화 TF-IDF 제출 (기준점 0.61+) + 세션 기준 검증 체계 구축
        [공통] 평가 서버 스펙 확인 (GPU/인터넷/용량/시간 제한)
2주차:  [B] LightGBM 피처 엔지니어링  ∥  [C] 트랜스포머 파인튜닝 (병행)
3주차~: 오류 분석 → 소수 클래스 보강 → 반복 제출
마감 전: [D] 앙상블 + threshold 최적화 → 최종 제출물 재현성 점검
```

**의사결정 원칙**: 모든 아이디어는 고정된 검증 분할의 Macro-F1로만 채택/기각을 결정하고, 리더보드 제출은 검증에서 이긴 것만 올린다.
